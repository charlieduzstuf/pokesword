# Pokemon Sword — decompilation status

Target: `Pokemon Sword[0100ABF008968000][US][v0].nsp` (base game, no update).
Engine: Game Freak **"orion"** native ARM64 C++ — *not* IL2CPP (RomFS contains
no `global-metadata.dat`; all game code lives in the `main` NSO).

Project layout follows decomp.me / decomp.dev conventions and is a fork of
`notyourav/pokesword`. See `README.md` for the layout and build instructions.

symbol and a place in the source tree. **Matching** means a C++ body exists and

## Reverse-engineering the remaining 128,239

`tools/auto_match.py` only matches functions whose bodies are mechanical. For the
rest, the work is understanding the code, and the accelerator is Ghidra's
decompiler, driven headlessly by `tools/ghidra_run.py`.

Ghidra imports `data/<module>.elf`, which already carries the recovered function
boundaries and 11,507 real names as ELF symbols, and then runs the decompiler
over every function that is not yet matched. Two choices make this tractable at
this scale:

- **Auto-analysis is skipped.** On a 25 MB `.text` with 100k functions it
  dominates wall-clock, and most of what it buys is type inference the
  decompiler re-derives per function anyway.
- **Matching functions are skipped.** They already have verified bodies, so
  decompiler budget goes to the gap.

Runs are resumable — output is appended and finished addresses are recorded in a
`.done` sidecar, so an interrupted run continues.

Ghidra's output does not itself match the original assembly, and the project does
not claim otherwise. What it provides is the C-like body, a real signature, and
the call graph for each of the 128,239 remaining functions, which is what makes
hand-matching them tractable.

      an external exporter are reused instead.

      pointer chasing).

      string-content-derived names, uniquely assigned per module.

## Known limitations

- **Matching rate is 15.92%, not 100%.** The 24,206 matched functions are the
  mechanically-solvable ones (leaf accessors, constants, comparisons, thunks,
  straight-line load/store sequences). The other 127,856 contain calls,
  branches, loops or vtable dispatch. Ghidra decompiles them
  (`tools/ghidra_run.py`), but its output is C-like pseudocode that does not
  compile back to the same assembly — turning that into matching code is
  per-function human work, and it is the bulk of what remains. The realistic
  ceiling for automation on this binary is around 20–25%.
- **Function names.** 11,507 of 152,062 (7.6%) carry a meaningful name rather
  than `sub_<addr>`. The binary is stripped; the rest needs manual RE. Ghidra
  imports the names that exist and its call graph helps infer more.
- **Matched bodies are at global scope.** Their signatures are *recovered* from
  the instruction stream, not chosen, so they cannot be moved into a namespace
  without changing the mangled name and invalidating the verification. Once the
  surrounding class structure is known from RTTI, they can be turned into
  members.
- **The dispatch-loop bodies in `decomp/<mod>/fn_*.c` are not idiomatic C++.**
  That is deliberate: it makes behavioural equivalence provable
  (`decomp/docs/verification.md`). The matching C++ lives in `prog/`.
- **`.prmb` data tables.** Headers identified and documented; deep format RE
  deferred to the community `jayztemplier/swordshield-data` project.
- **NX64 build via CMake is not exercised here** — this machine has no
  devkitA64 or Clang 5.0.1. Matching is verified by compiling with
  `clang --target=aarch64-none-elf` directly (`tools/match_harness.py`), and the
  host build is what has been executed.
