# Registering this project on decomp.dev

decomp.dev scrapes progress from GitHub Actions artifacts. This page records what
it actually requires, because the failure messages do not say it.

## The requirement

From decomp.wiki (`Tools -> decomp.dev`):

> The progress report should be uploaded as an artifact named `VERSION_report`
> (e.g. `SLUS_203.88_report`)
>
> ```yaml
> - name: Upload progress report
>   uses: actions/upload-artifact@v4
>   with:
>     name: ${{ matrix.version }}_report   # e.g. SLUS_203.88_report
>     path: build/report.json
> ```
>
> Progress reports can be generated using objdiff, and the protobuf schema is
> available to generate from your own tooling if desired.

Two hard requirements:

1. **Artifact name** must match `<VERSION>_report`.
2. **Contents** must include `report.json`, in **objdiff's protobuf**
   progress-report format.

decomp.dev must also be able to read the repository, so the project has to be
public and the workflow must run on the default branch.

## What went wrong first, and what the messages mean

Two different failures, and the difference between them is the useful part:

| decomp.dev message | meaning |
|---|---|
| `No workflows found in repository.` | It could not see `.github/workflows/` at all. Either the file is not on the default branch, or the repo metadata has not been fetched yet. |
| `No workflow runs containing reports found.` | It **found** the workflow and its runs, and could not find a report artifact in any of them. |

This project hit both in sequence. The first attempt uploaded an artifact named
`progress` containing `progress.txt`; the workflow itself was present and active
the whole time (`GET /actions/workflows` returned `total_count: 1`).

So the second message is progress, not a new failure: it means the workflow is
discovered and only the report is missing.

## Current state: name fixed, format not

`.github/workflows/progress.yml` now uploads an artifact named
`build562_report` containing `report.json`, which satisfies the **name**
convention.

`report.json` is **not** objdiff protobuf. `tools/progress_json.py
--format objdiff` writes this project's own JSON shape, with a `note` field
saying so, because:

- objdiff generates the report by diffing a built object file against the
  target, and this project **does not build through objdiff**. It has its own
  matching harness (`tools/match_harness.py`), whose verdict is authoritative
  and which the whole verification discipline is built on.
- Emitting objdiff's protobuf from these registries instead is possible --
  decomp.wiki notes the schema is published "to generate from your own tooling"
  -- but it would be a second, independent statement of what is matched, derived
  from the registries rather than from the harness that proved it. Two sources of
  truth for "what matches" is precisely the failure this project keeps hitting
  (three counting implementations, two of which drifted).

So until that decision is made deliberately, decomp.dev will list the project but
will not be able to chart it.

## Options, in order of preference

1. **Build through objdiff.** Make the project an objdiff target so the report
   is generated by diffing the built binary against the original, exactly as
   decomp.dev expects. This is the honest route: the report would then be derived
   from the same comparison the project already treats as authoritative. Cost is
   real — objdiff wants its own build definition and its own notion of section
   layout, and this project's linker arrangement is unusual.
2. **Emit objdiff protobuf from `match_progress.py`'s output**, using the
   published schema. Cheaper, but it means the progress report is a *restatement*
   of the registries rather than an independent measurement. Acceptable only if
   the same harness verdict is what feeds it.
3. **Do nothing.** The README badge and the `progress` job already report the
   figure, and CI fails on any verification mismatch. decomp.dev adds a chart
   and a public listing; it does not add correctness.

## Verifying a registration attempt

From the command line, which is faster than the web form:

```sh
gh api repos/charlieduzstuf/pokesword/actions/workflows --jq '.total_count'
gh api repos/charlieduzstuf/pokesword/actions/runs --jq '.workflow_runs[0] | "\(.name) \(.status)/\(.conclusion)"'
gh api repos/charlieduzstuf/pokesword/actions/runs/<id>/artifacts --jq '.artifacts[].name'
```

The third command is the one that matters: it should print a name ending in
`_report`. If it does not, decomp.dev will not find a report either.
